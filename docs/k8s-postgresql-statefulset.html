1. Fundamentos y Arquitectura de Estado en Kubernetes

El desafío del acoplamiento de identidad y datos en cargas transaccionales distribuidas

1.1 El Contrato de Estado: Deployment vs StatefulSet

En la computación nativa en la nube, las aplicaciones web y APIs suelen ser apátridas (stateless). Para estas cargas, el controlador estándar es el Deployment, el cual asume que los Pods son fungibles, efímeros y reemplazables en cualquier instante sin orden establecido.

Sin embargo, bases de datos relacionales como PostgreSQL exigen un contrato de estado riguroso: un nodo específico asume el rol de escritura (Primario) mientras otros nodos actúan como réplicas de lectura (Standby), sincronizando su estado mediante streaming de registros Write-Ahead Log (WAL).

Característica Deployment (Stateless) StatefulSet (Stateful)
Identidad de Red Efímera y aleatoria (api-78f997df7-kq9pz) Fija y determinista (postgresql-0, postgresql-1)
Orden de Despliegue Concurrente y sin dependencias Secuencial estricto (0 → 1 → 2 ...)
Almacenamiento (PVC) Volumen compartido o efímero (emptyDir) 1 PVC dedicado e independiente por réplica
Re-vinculación de Volumen No garantizada tras recreación de Pod El Pod 0 siempre recupera el PVC 0 tras reinicio

2. Preparación del Almacenamiento Dinámico (StorageClass)

Habilitando la provisión automática de volúmenes persistentes en clústeres locales Kubeadm

2.1 El Problema del Almacenamiento en Clústeres Kubeadm

En clústeres montados manualmente con Kubeadm, Kubernetes no cuenta con un proveedor de almacenamiento CSI preinstalado. Si se despliega un StatefulSet con volumeClaimTemplates sin una StorageClass predeterminada, los PVCs quedarán indefinidamente congelados en estado Pending.

Alerta de Infraestructura
Sin un StorageClass dinámico, Kubernetes emitirá el evento: "waiting for a volume to be created, either by dynamic provisioning or by manually creating a PersistentVolume".

2.2 Despliegue de Rancher local-path-provisioner

Aplicamos el controlador oficial ligero que mapea directorios de disco local en /opt/local-path-provisioner:

4. La Capa de Red: Headless Service y Servicios de Acceso

Resolución DNS canónica por Pod en CoreDNS y desacoplamiento de tráfico RW / RO

4.1 Por qué un Servicio Estándar no Sirve: Headless Service (clusterIP: None)

Un servicio ClusterIP estándar crea una IP virtual balanceada mediante iptables. La réplica de PostgreSQL necesita conectarse específicamente al Pod primario (postgresql-0), por lo que un balanceador aleatorio provocaría fallos de replicación. Al utilizar clusterIP: None, CoreDNS genera registros DNS directos hacia las IPs de cada Pod.

4.2 Resolución DNS Individual por Pod en CoreDNS

Formato de resolución generado automáticamente:

  • postgresql-0.postgresql-headless.default.svc.cluster.local → IP directa del Pod 0
  • postgresql-1.postgresql-headless.default.svc.cluster.local → IP directa del Pod 1

4.3 Separación de Tráfico: Servicio Primario (RW) y Servicio Réplicas (RO)

5. Despliegue del StatefulSet y Mecánica del InitContainer

Desmontando la magia: Bootstrap condicional con pg_basebackup y standby.signal

5.1 Anatomía del StatefulSet: replicas, serviceName y OrderedReady

El StatefulSet asegura el arranque secuencial estricto. El Pod 1 no inicia hasta que el Pod 0 haya superado satisfactoriamente sus sondas de preparación (readinessProbe).

5.2 Aislamiento de Volúmenes con volumeClaimTemplates

Cada réplica recibe un disco independiente de 1 GiB vinculado a la StorageClass local-path.

5.3 Desmontando la "Magia": Lógica Interna del InitContainer

El contenedor de inicialización evalúa el ordinal del Pod:

ORDINAL=${HOSTNAME##*-}
if [ "$ORDINAL" -eq 0 ]; then
  # Nodo Primario: Asegurar permisos chmod 700 y permitir que initdb cree la base
  mkdir -p "$TARGET_DIR" && chmod 700 "$TARGET_DIR"
else
  # Nodo Réplica: Esperar al primario y clonar con pg_basebackup
  until pg_isready -h postgresql-0.postgresql-headless -p 5432 -U postgres; do sleep 2; done
  if [ ! -s "$TARGET_DIR/PG_VERSION" ]; then
    pg_basebackup -h postgresql-0.postgresql-headless -p 5432 -U "$REPLICATION_USER" -D "$TARGET_DIR" -Fp -Xs -R -v
  fi
fi

kubectl delete pod postgresql-0 --now

7.2 El Comportamiento Real: Bloqueo de Escrituras y Réplica Estancada

Al intentar escribir mediante el servicio primario, las peticiones fallan inmediatamente con Connection refused. Al consultar a postgresql-1: 

kubectl exec -it postgresql-1 -- psql -U postgres -c "SELECT pg_is_in_recovery();"
 pg_is_in_recovery 
-------------------
 t
(1 row)

La réplica devuelve t (true). Kubernetes no la asciende de forma automática. K8s desconoce la semántica interna de PostgreSQL y se limita a intentar recrear el Pod caído.

7.3 El Peligro del Split-Brain por Promoción Manual no Coordinada

Si un operador ejecuta manualmente SELECT pg_promote(); en postgresql-1 sin aislar previamente el clúster, y más tarde el nodo primario original vuelve a levantarse, ambas instancias aceptarán escrituras independientes. Sus transacciones divergirán irremediablemente, provocando un escenario de Split-Brain que destruye la coherencia de datos del negocio.

7.4 Por qué las Primitivas Nativas no Pueden Resolver el Failover

Conclusión de Sistemas Distribuidos
El failover automático seguro requiere tres pilares que Kubernetes puro no provee: Detección de fallo confiable, Elección de líder por quórum (consenso) y Cercado forzado (Fencing) del nodo caído para impedir escrituras residuales.

8. La Brecha hacia la Producción: Por Qué Usamos Operadores

Por qué los Operadores de bases de datos son indispensables en producción

8.1 Matriz Comparativa: StatefulSet Manual vs. Operadores de Producción

Capacidad Requerida StatefulSet Manual Operador (CloudNativePG / Zalando / Crunchy)
Failover Automático No existe (Manual) Automático sub-segundo con elección de líder por consenso
Prevención de Split-Brain Ninguna (Alto riesgo) Garantizado mediante Fencing y quorum distribuido
Backups y PITR Scripts frágiles Integración nativa Barman/WAL-G a S3/GCS/MinIO
Rolling Updates Downtime transaccional Switchover planificado con cero caída de servicio
Pool de Conexiones Despliegue manual PgBouncer integrado y autogestionado

8.2 Capacidades Esenciales de un Operador (CloudNativePG, Zalando, Crunchy)

Un Operador de Kubernetes es un controlador inteligente en Go que emula la labor continua de un DBA experto, evaluando el catálogo de PostgreSQL cada segundo para orquestar la conmutación por error en milisegundos con cero pérdida de datos (RPO=0).

9. Resolución de Problemas Frecuentes (Troubleshooting)

Diagnóstico y solución de incidentes típicos en despliegues con estado

9.1 Error 1: PVCs en Estado Pending por Ausencia de StorageClass

Causa: No existe ningún StorageClass predeterminado en el clúster Kubeadm.

Solución: Aplicar manifests/00-local-path-storage.yaml y validar con kubectl get sc.

9.2 Error 2: initdb directory exists but is not empty (lost+found)

Causa: El sistema de archivos Ext4 genera la carpeta del sistema lost+found en la raíz del volumen montado.

Solución: Definir PGDATA: /var/lib/postgresql/data/pgdata para aislar el clúster en un subdirectorio limpio.

9.3 Error 3: Fallo en pg_basebackup (pg_hba.conf)

Causa: pg_hba.conf rechaza las conexiones de la subred del clúster.

Solución: Asegurar que pg_hba.conf autorice conexiones desde 10.244.0.0/16 para el usuario replicator.

9.4 Error 4: Permisos Denegados en Directorio de Datos (chown 999:999)

Causa: El volumen montado pertenece a root:root (UID 0) mientras PostgreSQL ejecuta como UID 999.

Solución: Ejecutar chmod 700 "$TARGET_DIR" en el initContainer antes de iniciar PostgreSQL.
